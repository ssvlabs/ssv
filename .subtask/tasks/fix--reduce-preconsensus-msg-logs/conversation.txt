<lead>
The current implementation tracks message counts per signer, but there's only 1 message per signer per duty, so counts aren't useful.

Instead, change to track TIMING information:
1. Record WHEN we received a message from each signer (relative to slot start time)
2. Track overall time to reach pre-consensus quorum

The summary log should show something like:
```
🎯 got pre-consensus quorum  
   time_to_quorum=0.8s  
   signer_timings=[{signer:1,at:+0.2s},{signer:2,at:+0.5s},{signer:3,at:+0.8s}]
   quorum_reached_by=3
```

Where `+0.2s` means "slot start time + 0.2 seconds".

To get slot start time, you can compute it from:
- slot number (from the duty)  
- genesis time and slot duration from networkconfig

Look at how other code computes slot timing, e.g., in `operator/duties/scheduler/` or `beacon/` packages.
</lead>

<worker>
- `BaseRunner` pre-consensus processing runs in a single per-role queue-consumer loop: `Validator.Start()` spawns one `StartQueueConsumer` per role, and that loop calls the handler synchronously (no concurrent handler calls). See `protocol/v2/ssv/validator/startup.go:22` and `protocol/v2/ssv/validator/queue_validator.go:80`.
- `basePreConsensusMsgProcessing` is only reached via `Validator.ProcessMessage → dutyRunner.ProcessPreConsensus` inside that same loop, so it’s not called concurrently for the same duty/runner. See `protocol/v2/ssv/validator/validator.go:129`.
- Timer timeouts enqueue messages into the queue; they don’t call runner methods directly, so they don’t introduce concurrent `ProcessPreConsensus` calls. See `protocol/v2/ssv/validator/timer.go:19`.
- Given the above, `preConsensusMsgLogMu` wasn’t protecting against any real concurrent access path; I removed it and the associated lock/unlock calls (`protocol/v2/ssv/runner/runner.go:85`, `protocol/v2/ssv/runner/preconsensus_msg_log.go:24`).
